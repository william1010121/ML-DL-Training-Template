# 實作紀錄

這個目錄記錄「做了什麼特別的」。README 說明怎麼用這個專案，`AGENTS.md` 規定必須遵守什麼規則，
`configs/*/research.md` 保存實驗結果——這三者都有明確的家。唯一沒有家的是實作過程中的取捨：
為什麼選了這條路、為什麼放棄了看起來更明顯的那條、是什麼約束逼出了現在這個做法。這些理由若只
留在 commit message 裡，實際上等於不存在，因為沒有人會為了理解一段程式碼去翻三個月前的 git log。

## 什麼該寫進來

門檻是**非顯而易見的決策**：改動了架構邊界、放棄了某個顯而易見的方案、或因為某個約束而繞了路。
例行的修 bug、新增實驗、調參數、跟著既有模式擴充功能，都不必寫——那些從程式碼和 commit 本身
就看得懂，寫進來只會稀釋真正重要的內容。

判斷標準可以是這個問題：三個月後有人看到這段實作，會不會問「為什麼不直接用比較簡單的做法」？
如果會，那個答案就該在這裡。

## 兩種文件

`decisions/` 放決策：面對什麼問題、有哪些選項、為什麼選了這個、代價是什麼。重點在 why。

`notes/` 放實作筆記：某個機制實際怎麼運作、關鍵檔案在哪、有什麼不明顯的陷阱。重點在 how，
寫給需要動這塊程式碼的人。這個目錄在第一篇筆記出現時才建立——空目錄無法被 git 追蹤，而模板的
初始化流程會拒絕刪除未追蹤的內容。

檔名用 kebab-case 描述主題本身，例如 `claude-code-adapter.md`，不要用日期或流水編號——編號會
逼人去查前一篇是幾號，主題名則可以直接搜尋。

## 寫法

用中文，簡短精要。以 heading 加段落為主體，一個 heading 底下寫成連貫的段落，不要每句話換行，
也不要把敘事拆成一堆條列——條列只適合真正並列的項目。一篇大約三十到六十行；寫不滿通常代表這個
決策沒有特別到需要記錄，明顯超出則多半混進了操作說明，那些屬於 README。

刻意不使用 Status / Context / Options / Decision 這類表單欄位。填欄位會把思考壓成碎句，而這裡
要的正好相反：經過思考、讀起來像在對人解釋的文字。

## 與研究紀錄的關係

`configs/research.md` 的 `## Global Decisions` 表格是索引，這裡是正文。寫完一篇後在該表格加一列，
附上 commit、一句話摘要，以及連到這份文件的連結。
